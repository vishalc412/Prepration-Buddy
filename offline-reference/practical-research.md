## Real local protocol versus standards implementation

The proposed MCP case deliberately implements a narrow stdio subset pinned to 2025-11-25. That revision documents initialize/version/capability lifecycle, followed by initialized notification. stdio requires newline-delimited JSON-RPC and keeps nonprotocol logging off stdout. Tool error results and protocol errors are distinct outcomes. The client should test those outcomes and correlation rather than mark any response successful. [Pinned lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [pinned transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), [pinned tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

The researched latest official revision is 2026-07-28 and uses a different self-contained/per-request core model. The prototype must not advertise current-revision conformance merely because it implements older initialize behavior. Implemented subset/version, unimplemented methods and compatibility expectations belong in both the case description and receipt. HTTP OAuth, audience/resource discovery and secure remote deployment remain design/optional extensions; fixture tokens are not OAuth. The current authorization guidance and security note forbid token passthrough to unrelated downstream resources. [Current core](https://modelcontextprotocol.io/specification/2026-07-28), [current authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [security practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).

## Java/Python local API prototype is not Spring/cloud proof

JDK HttpServer supports bound address/port listeners with registered handlers, providing an actual Java HTTP boundary without downloading a framework. That makes it useful for a dependency-light integration case, but does not demonstrate Spring configuration, repository transactions or production readiness. The case should bind loopback, cap inputs/deadlines, reject unauthorized objects and shut down its listener after tests. A real local request/response is stronger evidence than a diagram of an API, while still being narrower than a production service. [JDK HttpServer](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html).

Python's http.server documentation explicitly says it is not recommended for production. If used as a fixture interface, that boundary must be visible. It does not become secure enterprise hosting because a token comparison is added. The worked Java/Python contract must label fixed tokens as fixture identity and real OIDC/TLS, frontend validation, container security and cloud operation as separately tested integrations. [Python HTTP server](https://docs.python.org/3/library/http.server.html).

State durability needs actual persistence and recovery assertions. SQLite connection/transaction behavior should be configured deliberately; reopening a stored accepted task is different from an in-memory record surviving within one test process. A local transaction can establish atomic local outbox/state updates, while downstream delivery still needs idempotency and reconciliation. If the implemented enterprise case remains in memory, leave restart durability unimplemented rather than copying claims from another day's SQLite exercise. [Python SQLite](https://docs.python.org/3/library/sqlite3.html), [safe idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).

## Modernization and evaluation claims must stay bounded

A deterministic supported fixture change with actual Java build/behavior receipts teaches a credible modernization slice. OpenRewrite preview and recipe-based transformation remain useful external extensions, not labels for arbitrary regex replacement. Real CVE or dependency freshness claims require trustworthy catalog/advisory inputs and declared lookup dates. Report syntax/metadata checks as such. Same-runtime compiler-target tests do not prove behavior across source/target JDK deployments. [OpenRewrite Maven behavior](https://docs.openrewrite.org/reference/rewrite-maven-plugin).

The evaluation case uses declared task IDs, labels, candidate records, critical gates and reporting arithmetic. Data are fixed/synthetic unless a recorded run supplies observations. Cost units are teaching values, not model prices; copied latency values are supplied metrics, not measured HTTP/model latency. A lexical corpus is not an embedding encoder, and fixed response evaluation is not a live LLM benchmark. Add real model and production instrumentation only with a documented provider/runtime configuration and accepted dataset. [Evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [trace concepts](https://opentelemetry.io/docs/concepts/signals/traces/).

The adoption scorecard can demonstrate explicit denominators, baseline assumptions and expand/revise/stop rules. It cannot establish that AI caused a productivity improvement in a team that never ran the pilot. DORA's delivery measurements complement quality/review/cost/developer-experience evidence; usage counts alone are insufficient. [DORA delivery metrics](https://dora.dev/guides/dora-metrics/).

## Completion criteria

Before a planned case becomes runnable-local coverage, record the actual command, runtime versions, exit status, passed/failed checks, relevant artifact/source fingerprints and unresolved boundary. Parent-owned UI verification is separate from worker code execution. Keep every prototype limitation beside its runnable download. All topics can be mapped without pretending that every production qualification is implemented, every external platform integrated or every candidate credential demonstrated.
